## Задание 1. Анализ тональности

### Шаг 1. Данные

```python
dataset = load_dataset("cardiffnlp/tweet_eval", "sentiment")
```
TweetEval Sentiment — размеченный корпус твитов (конфиг `sentiment`): `0=negative`, `1=neutral`, `2=positive`. Используем конкретно потому, что ниже тот же проект (`cardiffnlp`) выпустил RoBERTa-модель, обученную ровно на этих метках — честное сравнение.

```python
df = dataset['train'].to_pandas()
df = df.groupby("label").sample(n=1000, random_state=42)
```
Из train берём ровно по 1000 на класс → 3000 текстов, строго сбалансированных. Так требует задание («не менее 3000, минимум 500 на класс»). `random_state=42` — воспроизводимость.

**Дедупликация** (`drop_duplicates(subset="text")`) — чтобы один и тот же твит не попал одновременно в train и test (утечка данных).

**Split 70/15/15** через два вызова `train_test_split` со стратификацией по `label` — это сохраняет пропорции классов в каждой из частей.

### Шаг 2. Предобработка

Для TF-IDF нужен нормализованный текст (одна форма слова, без мусора). Для VADER и Transformer — наоборот, сырой текст с эмоциональными маркерами. Поэтому строим обе версии.

- **lowercase** — убирает различие `Good`/`good`.
- **word_tokenize** — делит на токены по правилам NLTK (учитывает `n't`, `can't`).
- **`isalpha() or == "n't"`** — выбрасывает цифры, пунктуацию, URL-мусор, но сохраняет отрицания.
- **stopwords − {not, no, nor, never, n't}** — стандартные стоп-слова, но оставляем отрицания, иначе `"not good"` → `"good"` и тональность инвертируется.
- **WordNetLemmatizer** — приводит слово к базовой форме (`running`→`run`), не трогая отрицания. Используется только для TF-IDF.

**Главный пункт устной защиты**: «чем больше чистишь — тем хуже для словарных и Transformer-моделей». Пример: `"this is NOT good!"` после удаления `not`, пунктуации и регистра → `"good"` — положительный. Поэтому VADER и Transformer ниже получают **исходный `text`**, а не `clean_text`.

### Шаг 3. VADER

```python
sia = SentimentIntensityAnalyzer()
sia.polarity_scores(text)["compound"]
```
VADER — словарно-правиловой анализатор (лексикон + правила на отрицания/усилители). `compound` — агрегированная оценка от −1 до +1.

**Подбор порогов на валидации.** Два порога `low`, `high`: `score <= low` → negative, `score >= high` → positive, иначе neutral. Делаем сетку по шагу 0.05, выбираем ту пару, что даёт лучший `macro-F1` на валидации. **Критично**: подбор только на `val_df`, оцениваем на `test_df`. Иначе — утечка.

### Шаг 4. TF-IDF + Logistic Regression

```python
TfidfVectorizer(ngram_range=(1,2), min_df=2, max_df=0.95)
```
- `ngram_range=(1,2)` — ловим и слова, и биграммы (`not good`).
- `min_df=2` — слово должно встретиться минимум в 2 документах (отсекаем опечатки).
- `max_df=0.95` — исключаем слишком общие слова.

**Важно**: `fit_transform` только на `training_df`, на val/test — `transform`. Иначе TF-IDF «подсматривает» в тестовую лексику → утечка.

Две конфигурации LogisticRegression:
1. `C=1.0, class_weight=None` — стандарт.
2. `C=4.0, class_weight="balanced"` — слабее регуляризация + веса классов (хотя у нас сбалансировано, этот вариант иногда помогает за счёт меньшей регуляризации).

Выбираем лучшую по `macro-F1` на валидации, тестируем на тесте.

### Шаг 5. Transformer

```python
model_name = "cardiffnlp/twitter-roberta-base-sentiment-latest"
```
Эта модель обучена на TweetEval + свежем корпусе твитов (~124M твитов). Возвращает ровно 3 метки `negative/neutral/positive` в нижнем регистре → мэпим на 0/1/2.

```python
clf = pipeline("sentiment-analysis", ..., truncation=True, max_length=128)
```
`max_length=128` — твиты редко длиннее, не замедляем GPU. `batch_size=32` — компромисс между скоростью и памятью.

Без дообучения — задание разрешает (fine-tuning опционален). Это zero-shot использование pretrained-модели.

### Шаг 6. Сравнение

Собираем метрики (accuracy, precision_macro, recall_macro, f1_macro) в таблицу. Три confusion matrix рядом — наглядно видно, какая модель какие пары путает.

### Шаг 7. Ошибки

Берём 10 случайных примеров, где **хотя бы одна** модель ошиблась — удобно сравнивать между собой. По моему опыту с TweetEval:

- TF-IDF+LR средне — выучивает частотные эмоциональные слова, но без контекста.

### Шаг 2. Предобработка

Для суммирования нам нужны **исходные** предложения, которые пойдут в итоговое резюме. Поэтому — только нормализация пробелов и `sent_tokenize` (деление на предложения). Никакого удаления стоп-слов на этом этапе.

### Шаг 3. TextRank

```python
TfidfVectorizer(stop_words="english").fit_transform(sentences)
cosine_similarity(vec)
networkx.pagerank(graph)
```
TextRank = PageRank на графе предложений. Узлы — предложения, рёбра взвешены косинусной близостью их TF-IDF-векторов. Пред­ложение «важно», если оно похоже на много других важных.

- `fill_diagonal(sim, 0)` — убираем самосвязи, иначе предложение «важно само себе».
- Из каждого документа берём топ-3 → 15 кандидатов.
- Из 15 — снова TextRank, берём топ-6, восстанавливаем исходный порядок (`sorted(top6_idx)`).

### Шаг 4. BART

```python
summarizer = pipeline("summarization", model="facebook/bart-large-cnn")
```
BART-large обучен на CNN/DailyMail — умеет суммировать новостные тексты. Это абстрактивный метод: генерирует новый текст, а не выбирает предложения.

**Иерархическая стратегия**: каждый документ → короткое summary (90 слов), объединяем 5 summary, снова суммируем (150 слов). Так обходим ограничение BART на длину входа (~1024 токенов).

`do_sample=False, num_beams=4` — детерминированный beam search, воспроизводимый результат.

### Шаг 5. ROUGE

```python
rouge_scorer.RougeScorer(["rouge1","rouge2","rougeL"], use_stemmer=True)
```
- ROUGE-1 — пересечение униграмм (одиночных слов).
- ROUGE-2 — пересечение биграмм (пар слов подряд) → ловит связность.
- ROUGE-L — длина наибольшей общей подпоследовательности → порядок слов.

`use_stemmer=True` — считает `cat` и `cats` одним словом.

**Что говорить на защите**: ROUGE — автоматика, она не ловит фактическую точность. Высокий ROUGE ≠ правдивое резюме. Поэтому нужен и ручной качественный анализ.

### Шаг 6. Качественный анализ

Таблица в маркдауне — читается сразу. Главный пункт: **BART (абстрактивный) часто галлюцинирует** — добавляет цифры, имена, обобщения, которых не было в источнике. Экстрактивный от этого свободен (ровно слова из текста), но часто разорванный по связности.

from datasets import load_dataset

Поэтому `.map(dict)` падает с `unhashable type` — используем `.apply(pick_genre)`, где `pick_genre` берёт **первый** элемент массива, приводит к нижнему регистру и маппит через `genre_map`:
- `rap` и `hip-hop` объединяем в один класс **Hip-Hop**,
- оставляем 4 жанра из задания: Pop, Rock, Hip-Hop, Country.

Фильтр `df_full["language"] == "english"` — в датасете есть и другие языки, нам нужны только английские тексты. Потом: отбрасываем песни короче 200 символов (куплет из припева не считается песней), дедупликация по `lyrics`, сэмпл **ровно 300** песен на жанр (`random_state=42`). > Распаковать в `assignment3/`, читать `pd.read_csv("csv/Pop.csv")` и склеивать.

### Шаг 2. Предобработка

Для песен специфично: `[Chorus]`, `[Verse 1]` — убираем регуляркой `\[.*?\]`. Остальное стандартно: lower, только латиница, токенизация, стоп-слова, лемматизация. Короткие токены (≤2 символов) отсекаем.

### Шаг 3. Частотность

Считаем топ-10 слов на каждый жанр через `collections.Counter`. Абсолютная частота + относительная (доля от всех токенов жанра) + столбчатые диаграммы. Для сравнения жанров — относительная важнее (размер корпусов разный).

### Шаг 4. Лексические категории

Три словаря (время, эмоции, части тела). Для каждого жанра — сумма вхождений слов категории, **нормализованная** на 1000 токенов этого жанра. Иначе большой жанр всегда будет впереди.

Что ищем: Country должен лидировать по «time» (morning, night) и «body» (heart), Pop — по «emotion» (love), Hip-Hop часто беднее по этим «мягким» категориям.

### Шаг 5. Редкие vs TF-IDF

- **Редкие слова** (hapax, ≤3 вхождения): считаем через `Counter`, фильтруем. Это чаще всего имена, опечатки, случайные формы — информативность низкая.
- **TF-IDF** на уровне жанра: склеиваем все песни жанра в один «документ», получаем 4 документа. Высокий TF-IDF у слова = часто в этом жанре + редко в других. Это именно то, что нужно для классификации.

На защите: **TF-IDF лучше редкости для определения жанра**, потому что берёт **различающую** лексику, а не просто редкую.

### Шаг 6. Классификация

Split 80/20 стратифицированный. TF-IDF обучаем **только на train**. Две модели:
- **MultinomialNB** — быстрая, работает хорошо на bag-of-words, baseline.
- **Logistic Regression** — обычно побеждает за счёт лучшей обработки корреляций между признаками.

Параметры TF-IDF: `ngram_range=(1,2)` — слова и биграммы, `min_df=3` — отсечь редкие (их уже обсудили в Шаге 5), `max_df=0.9` — отсечь слишком общие.

Берём 5 случайных неверных предсказаний. Самые частые пары путаницы:
- Pop ↔ Rock (общая лексика любви/жизни/вечеров)

**Главный тезис**: одного текста недостаточно для жанра. Pop-баллада и Country-баллада лексически похожи — различия в ритме, инструментах, вокале. Текст — только часть сигнала.

### Шаг 7. Ошибки

## Контрольные вопросы — короткие ответы

Если спросят, вот сжатые ответы на все 25 вопросов из PDF.

1. **Словарь vs ML vs Transformer** — словарь использует фиксированный лексикон (быстро, прозрачно, слабо на сарказме); ML учится на размеченных данных (bag-of-words, игнорирует порядок); Transformer учитывает контекст, порядок слов и обучен на миллиардах токенов.
2. **TF-IDF** — вес слова = частота в документе × log(обратная документная частота). Высокий вес — часто в этом документе и редко в остальных.
3. **Train/val/test** — val для выбора гиперпараметров, test — для честной финальной оценки. Иначе переоценим качество.
4. **Macro F1 vs Accuracy** — accuracy зависит от доли большого класса; macro F1 — среднее F1 по всем классам, честно для несбалансированных данных.
5. **Confusion matrix** — показывает, какие классы с какими путаются; видно, где именно ошибается модель.
6. **Токенизация** — задаёт единицу анализа. Плохо потокенизировано → весь pipeline деградирует.
7. **Удаление стоп-слов и тональность** — отрицания (`not`, `no`) формально стоп-слова, но их удаление инвертирует смысл.
8. **Экстрактивное vs абстрактивное** — экстрактивное выбирает готовые предложения (точно, но несвязно); абстрактивное генерирует новый текст (связно, но может галлюцинировать).
9. **TextRank** — PageRank на графе, где рёбра — похожесть предложений (cosine на TF-IDF). Важные предложения — те, с которыми похожи многие.
10. **ROUGE-1/2/L** — пересечение униграмм / биграмм / длиннейшей общей подпоследовательности; измеряют лексическое совпадение с эталоном.
11. **Галлюцинации** — модель генерирует факты, которых нет в источнике.
12. **Фактическая согласованность** — ROUGE её не проверяет; нужно вручную сверять цифры, имена, события.
13. **Частота vs TF-IDF** — частота считает одно слово в одном документе; TF-IDF взвешивает частоту обратной документной частотой, выделяя различительные слова.
14. **Размер датасета** — малый датасет → переобучение, большая дисперсия метрик, модели не выучивают редкие классы.
15. **Дисбаланс классов** — модель смещается к большинству; macro F1 покажет провал, accuracy — нет.
16. **Char n-grams** — последовательности из N символов; ловят подписи письменности и типичные окончания, устойчивы к коротким и шумным текстам.
17. **Специфические символы** — казахские буквы (`ә, қ, …`) однозначно идентифицируют язык, если их не удалить.
18. **Короткие тексты и язык** — мало сигнала, особенно если слова общие (имена собственные, цифры).
19. **Code-switching** — классификатор возвращает один язык, а в тексте их два; метрики одноязычной классификации к этому неприменимы.
20. **Шум** — ошибки символов разрушают word-tokens, char n-grams страдают меньше.
21. **Утечка данных** — тестовые примеры (или их признаки) просачиваются в train. Признаки: подозрительно высокая точность, модель «знает» ответы.
22. **Pretrained Transformers** — плюсы: высокое качество, zero/few-shot; минусы: большой размер, медленно, непрозрачно, bias из обучающего корпуса.
23. **Несколько метрик** — одна метрика скрывает перекосы; например, accuracy при дисбалансе выглядит высокой при провале на меньшинстве.
24. **Анализ ошибок** — показывает **почему** модель ошибается (отрицания, сарказм, редкая лексика), а не только насколько часто.
25. **Воспроизводимость** — фиксируем random_state, версии библиотек, модели, препроцессинг; публикуем код и данные.
